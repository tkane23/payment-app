# 0010 モック明細の形式と正解データ

- ステータス：決定
- 日付：2026-09-27
- 関連ストーリー：E00-S03

## 背景

アグリゲーターとの契約前から、検出・診断のロジックを開発・テストする必要がある。受け入れ条件のケースのうち、未使用（利用者の回答）、解約後請求（解約の報告）、年額化候補（年額プランの価格）は、明細だけでは表せない。

## 選択肢

| 論点 | 選択肢 |
| --- | --- |
| 作り方 | JSON を手で書く ／ 生成スクリプトで作る |
| サービス名 | 実在の名前 ／ 架空の名前 |
| 明細以外の情報 | 持たない ／ 補助データとして持つ |
| 正解データ | 判定ルールの出力 ／ 本当の定期課金（ground truth） |

## 決定

- **作り方**：固定シードの生成スクリプト（`packages/shared/src/fixtures/build.ts`）で作り、出力した JSON をコミットする。JSON を手で書き換えた場合は、テストで検出する。
- **サービス名**：実在の名前と、明細の表記に近い文字列（例：`NETFLIX.COM`）を使う。サブスク辞書（E03-S02）の開発にも使えるため。金額は架空の値で、実際の価格とは一致しない。人物・口座・不動産会社や保険会社などの契約先は架空にする。
- **補助データ**：「使ってる？」への回答（`usageAnswers`）、解約の報告（`cancellations`）、年額プランの価格（`plan-prices.json`）を持つ。
- **正解データ**：本当の定期課金を正解とする。ただし、すべての正解が MVP の判定ルール（28〜33日間隔、金額差±10%）を満たし、定期課金でない支払いは満たさないように作る。E03-S01 の適合率・再現率をこのデータで測れるようにするため。
- **App Store のまとめ表示**：定期課金として正解に含め、`bundledBreakdown` に実際の内訳を参考として持つ（E05-S01 のテストに使う）。
- **年額払い**：12か月の中で1回しか現れないため、定期課金の正解には含めない。

サービス名と App Store の扱いは推奨案で進めた。プロダクトオーナーが PR で確認する。

## 影響

- 明細の型（`Account`・`Transaction`）は `packages/shared` に置き、E02-S01 の `AggregatorAdapter` もこの型を返す。
- ケースを増やすときは `build.ts` を直し、`pnpm --filter @payment-app/shared fixtures:generate` で JSON を作り直す。
- 年次（360〜370日）の判定を検証するには12か月より長いデータが必要になる。E03-S01 で必要なら期間を延ばす。
