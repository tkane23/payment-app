# レコメンドの設計原則

すべての提案は次の7原則を満たします。`packages/core` の提案の型は、この原則を必須項目として表現します（ストーリー E04-S01）。

| 原則 | 中身 | 型での表現（例） | 例 |
| --- | --- | --- | --- |
| 1. 自分ごとの根拠 | 利用実態、世帯構成、携帯キャリア、保有カードを踏まえる | `evidence: string[]` | 「先月は2回しか見ていません」 |
| 2. 金額と計算式を示す | 年間の削減額と計算方法 | `annualSavingYen: number`, `formula: string` | 「月1,490円×12−年額14,900円＝年2,980円」 |
| 3. 選択肢を並べる | 代わりの案2〜3個、「今のまま」を含む | `options: Option[]`（`keepAsIs` を必ず含む） | 「年額に切り替え／下位プラン／今のまま」 |
| 4. 失うものも伝える | 画質、同時視聴数、データの引き継ぎ、解約期限など | `tradeoffs: string[]` | 「下位プランでは画質がHDまで」 |
| 5. タイミングを選ぶ | 更新前、違約金のかからない月、キャンペーン中 | `recommendedAt: Date`, `timingReason: string` | 「更新の10日前です」 |
| 6. 全体で最適にする | キャリア特典・カード還元・サブスクの組み合わせ全体で最安を探す | `scope: 'single' \| 'portfolio'` | 「携帯プランを変えると動画2つが特典に含まれ月1,200円安い」 |
| 7. 何もしない提案もする | 最適なら「見直し不要」と言い切る | `kind: 'no_action_needed'` | 「今の組み合わせが最安です」 |

差別化の核は原則6と7です。

## 表現のルール

- 確信度が低い提案は断定しない。「もし使っていなければ」のような条件つきの表現にする。
- 削減額は年額で表示する。
- 「不要」と回答された提案は一定期間（初期値90日）出さない。
- 提案の並び順は「年間削減額 × 確信度 ÷ 実行の手間」のスコア順。

## 精度を上げ続ける仕組み

- 提案への反応（やる・あとで・不要）と理由を記録する。
- 「不要」の理由が「使っている」なら、未使用の判定基準を見直す。
- 提案の種類ごとに実行率を計測し、実行されない提案は根拠や出し方を改める。

## 判定ルール（MVP初期値）

| 提案の種類 | 判定条件 |
| --- | --- |
| 定期課金の検出 | 同じ支払先へ、月次（28〜33日間隔）または年次（360〜370日間隔）で、金額差±10%以内の支払いが2回以上 |
| 重複 | 同カテゴリーに2件以上、または同サービスに複数課金 |
| 未使用 | 「使っていない」と2か月連続で回答 |
| 年額化 | 月額で6か月以上継続し、安い年額プランがある |
| 支払い経路 | 特典・還元を踏まえた年間差額が閾値以上 |
| 値上げ | 前回より増額 |
| トライアル終了・更新 | 初回課金の前（3日前）、年額更新の前（10日前） |

閾値はすべて設定値として外に出し、コードに直書きしない。
